# Monorepo migration with independent Spring Boot backend

Species Atlas migrates from an external water ecology API to a self-contained stack: a Vue 3 frontend moved into `species-atlas-web/` and a new Spring Boot 3.2 backend in `species-atlas-server/`. The backend provides JWT-based auth, Flyway-managed MySQL schema, and five species CRUD endpoints matching the original API shape. Docker Compose orchestrates all services with bind-mount persistence to `.data/`. The migration is structurally sound — good separation of concerns, proper use of BCrypt for passwords, stateless JWT with access/refresh token distinction — but ships with a few security and operational gaps that need attention before production.

**Watch for:** Default JWT secret committed in source files (confirmed). Admin password `admin123` seeded via Flyway migration with no forced rotation (confirmed). No token revocation mechanism — logout is client-side only (confirmed). MySQL slow query log path in `my.cnf` may fail on first boot due to missing directory (likely).

**Verdict**: NEEDS_CHANGES

---

## High-level view

The architecture cleanly separates frontend and backend into sibling directories, each with its own Dockerfile. The frontend proxies `/api/` to the backend through nginx; in development, Vite does the same via its dev server proxy. This avoids CORS complexity and keeps the API surface unified.

JWT security follows modern patterns — HMAC-SHA256 via jjwt 0.12, separate access and refresh tokens with different TTLs, type claim to prevent refresh tokens from being used as access tokens. BCrypt handles password storage. The gap is in secret management: a working secret is hardcoded in `application.yml` and `docker-compose.yml`, and the logout endpoint does nothing server-side, so stolen tokens remain valid until expiry.

Database migrations use Flyway with versioned scripts from V1.0.0 through V1.1.0. Tables use soft delete (`deleted` column), audit columns (`create_time`, `update_time`, `create_by`, `update_by`), and appropriate indexes. The admin user is seeded with a pre-hashed password but there's no mechanism to force a password change on first login.

Docker persistence binds `.data/` into containers for MySQL data, uploads, and logs. This is simpler than named volumes and makes backups easier, but the MySQL `my.cnf` references `/var/log/mysql/slow.log` which isn't in a mounted directory and may not exist on container start.

<summary>Issues (7)</summary>

1. **Default JWT secret in source** — `application.yml` and `docker-compose.yml` contain working JWT secrets. Remove or replace with invalid placeholders that force configuration before startup.

2. **Seeded admin password with no rotation** — The Flyway migration inserts `admin/admin123`. Add a flag or separate initialization flow that forces password change on first admin login.

3. **No token revocation** — Logout is purely client-side. If a token is stolen, it remains valid until TTL expires. Consider a token blacklist (Redis-backed) or short-lived access tokens with sliding refresh.

4. **MySQL slow log directory missing** — `my.cnf` sets `slow_query_log_file=/var/log/mysql/slow.log` but that directory isn't mounted and may not exist in the container, causing MySQL to fail or skip slow logging silently.

5. **Dev MySQL shares data directory with prod** — Both `docker-compose.yml` and `docker-compose.dev.yml` mount `.data/mysql`. Running both environments sequentially could cause data conflicts or accidental prod data deletion.

6. **Open registration endpoint** — `/auth/register` is in the whitelist with no rate limiting or approval flow. In production this allows unlimited user creation.

7. **Actuator endpoints exposed without auth** — `/actuator/**` is whitelisted. Restrict to health/info only or require authentication.

### JWT secret management

The secret flows from three places with decreasing priority: environment variable `JWT_SECRET`, then `application-prod.yml` (which reads `${JWT_SECRET}`), then `application.yml`'s default. The problem is `application.yml` contains a fully functional 64-byte secret:

```yaml
jwt:
  secret: ${JWT_SECRET:species-atlas-jwt-secret-key-2024-should-be-at-least-256-bits-long}
```

`docker-compose.yml` duplicates this pattern:

```yaml
JWT_SECRET: ${JWT_SECRET:-species-atlas-jwt-secret-key-2024-production-environment-should-be-changed}
```

Anyone who clones the repo and runs `docker-compose up` gets a working system with a known secret. Replace these defaults with obviously-invalid placeholders (e.g., `CHANGE_ME_BEFORE_PRODUCTION_64_CHARS_MINIMUM`) that will fail HMAC key validation if used directly.

### Admin user seeding

`V1.1.0__init_admin_user.sql` inserts:

```sql
INSERT INTO sys_user (username, password, ...)
VALUES ('admin', '$2a$10$N.zmdr9k7uOCQb376NoUnuTJ8iAt6Z5EHsM8lE9lBOsl7iAt6KhOq', ...)
```

The BCrypt hash corresponds to `admin123` as documented in the README. This is fine for development but dangerous in production — the password is publicly known. Options: (a) add a `must_change_password` column and enforce it on login, (b) seed with a random password and print it to logs on first startup, or (c) move admin creation out of Flyway into a separate bootstrap script.

### Token lifecycle and revocation

`JwtAuthenticationFilter` validates tokens and loads the user from the database on each request, but the filter doesn't check a revocation list. `AuthController.logout()` returns success without any server-side action:

```java
@PostMapping("/logout")
public ApiResponse<Void> logout() {
    // JWT 是无状态的，退出登录只需客户端清除 Token
    return ApiResponse.success("退出成功", null);
}
```

The refresh token flow in `AuthServiceImpl.refreshToken()` issues new tokens without invalidating the old refresh token, allowing unlimited refresh cycles from a single stolen token. For a species data platform this may be acceptable risk, but note that compromised tokens have a 7-day window (refresh TTL).

### MySQL configuration and persistence

`docker/mysql/conf.d/my.cnf` enables slow query logging to `/var/log/mysql/slow.log`. The Docker Compose file doesn't mount a volume at `/var/log/mysql/`. On Alpine-based images this directory may not exist, causing MySQL to either fail startup or silently skip slow logging. Either mount a volume for MySQL logs or change the log path to `/var/lib/mysql/slow.log` (inside the data directory that is mounted).

Both compose files mount the same `.data/mysql` path. If a developer runs `docker-compose -f docker-compose.dev.yml up`, seeds test data, then runs `docker-compose up` for prod testing, they'll be working against the same database. The dev compose should use `.data/mysql-dev` or a separate directory.

### Security filter configuration

The whitelist in `SecurityConfig` includes `/actuator/**`:

```java
private static final String[] WHITE_LIST = {
    "/auth/login",
    "/auth/register",
    ...
    "/actuator/**"
};
```

Spring Boot Actuator exposes health, info, and potentially env/configprops endpoints depending on configuration. The default `application.yml` doesn't explicitly restrict which actuator endpoints are exposed. In production, consider either removing `/actuator/**` from the whitelist and protecting it behind auth, or explicitly configuring `management.endpoints.web.exposure.include=health,info`.

### Dead JPA index annotation

The User entity defines `@Index(name = "idx_username", columnList = "username", unique = true)` via JPA annotations, but Flyway also creates `UNIQUE INDEX idx_username (username)` in the migration. Since `ddl-auto: none`, JPA won't create indexes — the annotation is now dead documentation and could be removed for clarity.

### No nginx rate limiting

The nginx config has no rate limiting. Combined with the open `/auth/register` endpoint, this allows unlimited registration requests. Consider adding `limit_req_zone` for auth endpoints.
